# A/B 多机 Agent 开发与应用验收规范

- 版本：v1.0
- 日期：2026-11-14
- 性质：根据用户已确认的讨论整理，供后续项目重复引用。
- 当前范围：A、B 两端的任务调度、隔离开发、源码审查、实际应用验收与合并。
- 实施状态：本文件是协作规范，不代表远程通信、持久会话、测试入口或自动调度已经实现或验证。

## 1. 核心目标

以实际应用结果为导向：B 将需求实现并运行起来，A 亲自操作应用，验证业务结果达到预期，之后才进入最终合并。

代码修改完成、构建成功、B 自测通过、Git 推送成功，均不单独构成最终验收通过。

基本原则：

1. A 统一调度、监督、源码审查和应用验收；B 负责规划、开发、自测及运行待验收应用。
2. 每个任务优先创建新的本地分支，并配备独立 worktree；不直接在目标主分支开发。
3. B 必须经历“规划 → 处理 → 测试/审查”，问题修复后重新验证。
4. 涉及底层框架选择，必须说明推荐理由，与另外两个同类产品比较，等待用户确认。
5. 测试证据、源码审查和运行实例绑定具体代码版本。
6. 开发可以并行，同一目标分支的最终集成串行处理。
7. 合并与生产部署分离。

## 2. 角色分工

| 角色 | 职责 | 交付要求 |
|---|---|---|
| 用户 | 提出需求、确认框架选型、决定重大范围变化及最终合并 | 明确决定并记录所对应的方案或版本 |
| A：调度与验收端 | 识别项目、制定验收标准、派发任务、监督进度、审查源码、实际操作应用、记录缺陷、复验及组织集成 | 提供基于实际操作和业务结果的验收报告 |
| B：开发与运行端 | 检查项目、制定计划、隔离开发、自测、运行待验收项目、准备测试数据、维护实例、修复问题 | 提供代码版本、运行入口、测试结果与日志 |
| Linux C：未来生产端 | 当前暂不引入；未来用于最终确认版本的 Git 同步及部署设置 | 不承担当前开发测试，不自动参与流程 |

A 应亲自使用应用，不以转述 B 的自测结果代替应用验收。独立源码审查优先使用区别于实现者的 Agent 会话；B 自审不作为唯一审查。

## 3. 多项目和工作目录隔离

一个工作区可以处理多个项目。A 为每个项目登记：

- 项目标识、仓库位置及代码交接方式。
- 目标分支、开发基准版本、项目目录范围。
- 运行环境、依赖管理方式、构建与测试命令。
- 启动方式、应用类型、测试入口及核心业务流程。
- 提交、推送、合并的执行权限约定。

每个任务登记项目、任务 ID、分支、worktree、执行次数标识及依赖关系。示例分支：

```text
agent/<project>/<task-id>-<short-description>
```

独立 worktree 的创建示意（执行时替换占位符）：

```bash
git worktree add -b agent/PROJECT/TASK-short-description WORKTREE_PATH BASE_SHA
```

分支创建前检查仓库状态，保留已有用户修改。并行任务除代码目录外，还应隔离端口、构建输出、临时文件、数据库测试数据和容器资源。

多个项目属于同一 monorepo 时，共用仓库级合并队列，以目录范围区分项目。跨仓库需求通过父任务协调，每个仓库独立验证与集成，不将其视为天然原子操作。

## 4. 标准执行流程

```text
用户提出需求
  → A 明确项目、范围、依赖和业务验收场景
  → B 检查现状并输出计划
  → 涉及框架选择：三方案比较 → 等待用户确认
  → A 检查计划
  → B 创建新本地任务分支与独立 worktree
  → B 实现、自测、整理交付证据
  → B 运行交付版本，提供可访问的验收实例
  → A 源码审查、实际应用操作验收
      → 有问题：A 记录缺陷 → B 修复并更新实例 → A 复验与回归
      → 通过：进入项目合并队列
  → 形成与最新目标分支结合的候选合并结果
  → B 运行候选版本，A 验证受影响场景与核心流程
  → 按用户确认规则合并
  → 合并后检查、输出报告、归档
```

没有实施计划不进入开发。框架选择待确认时，暂停依赖该选择的实现；可继续只读调查，其他无依赖任务可以继续。

## 5. 底层框架选型确认

引入或替换应用框架、数据库、ORM、消息队列、Agent 编排、任务调度、跨机通信框架等形成长期约束的基础依赖时，触发选型确认。沿用已确认技术栈的常规功能开发无需重复选型。

选型报告必须包含一个推荐方案和另外两个同类产品：

| 比较项 | 推荐方案 | 同类产品一 | 同类产品二 |
|---|---|---|---|
| 对当前需求的适配度 | 待填 | 待填 | 待填 |
| 主要优势 | 待填 | 待填 | 待填 |
| 主要劣势 | 待填 | 待填 | 待填 |
| Windows/Linux 支持 | 待填 | 待填 | 待填 |
| 与现有项目的兼容性 | 待填 | 待填 | 待填 |
| 开发、维护与运行成本 | 待填 | 待填 | 待填 |
| 测试与可观测性 | 待填 | 待填 | 待填 |
| 维护状态、生态和许可证 | 待填 | 待填 | 待填 |
| 迁移、回退与退出成本 | 待填 | 待填 | 待填 |

结论回答：为什么选择推荐方案、为何另外两个方案当前较不适合、需要接受哪些代价。对有时效性的事实记录来源及核查日期，尚未验证的性能或兼容性标记为待验证。

确认记录绑定任务 ID、方案版本、用户决定。更换框架或实质改变方案时重新确认；确认前不提前安装所选框架或按该方案改写项目结构。

## 6. Git 交接与源码审查

推荐 A、B 各自保有同一项目的独立仓库副本，不共同写入一个开发目录。

- 提交记录和推送事件用于定位交付版本，不代替源码审查。
- A 获取 B 交付的明确版本，检查相对基准的差异及完整调用上下文。
- A 阅读源码不必安装全部运行依赖；需要本地构建复现时再准备依赖。
- 有共享远端时通过任务分支交接；没有共享远端时可采用 Git bundle 等方式。
- 任务分支推送不等于合并主分支。提交、推送须按用户明确约定执行，本文件本身不触发任何 Git 操作。

A 至少检查修改范围、实现逻辑、异常路径、兼容性、配置与依赖变化、测试覆盖及各项业务验收条件。

## 7. B 的运行实例交付要求

B 负责启动项目，A 负责实际访问和使用。验收实例必须满足：

1. A 能访问前端以及其依赖的后端接口，而非仅能打开一个静态页面。
2. 使用隔离测试环境与测试数据，不借用生产数据和生产实例开展开发测试。
3. 标识运行版本、构建产物和实例，确认验收源代码无额外未记录修改，产物已更新。
4. 验收期间冻结实例，避免后台热更新使验收对象漂移。
5. B 修复后交付新版本并重启或重建实例，A 对新版本复验。
6. 提供日志位置或查询方式，保证验收期间服务可用。
7. 凭据仅记录引用，不在报告或普通项目文件中写入密码、私钥、Token、Cookie 等秘密。

Web 项目由 A 通过浏览器操作；API 项目由 A 发出真实请求并验证结果；桌面应用需有可操作的桌面入口。工具或访问条件不足时记录为阻塞或未验证，不计作验收通过。

如需 Linux 兼容性验证，另行准备隔离测试环境，当前不接入 Linux C 生产机。

## 8. 结果导向的应用验收

验收场景在任务派发时制定，逐项写明：前置条件、测试数据、操作步骤、预期结果、实际结果、证据和结论。

至少根据任务适用性覆盖：

- 需求对应的正常业务路径。
- 空数据、边界值、重复操作等边界情形。
- 权限差异及异常处理。
- 数据持久化、刷新后状态、重新打开后的结果。
- 修改关联的核心业务回归。

截图是辅助证据。保存操作应核对数据实际落地，导出操作应打开文件核对内容，不以成功提示代替真实结果。

例如订单导出：选择筛选条件 → 导出 → 打开文件 → 核对字段和记录 → 验证空结果及权限场景 → 回归查询、分页和详情。

缺陷记录必须包含复现步骤、预期与实际差异、版本、实例、证据及严重程度。B 修复后，A 复验该缺陷并检查相关回归；保留中间失败原因及修正方式。

## 9. 并发、重试与集成

- 同一任务同一时刻只有一个有效写入者。
- 任务重试或换执行端时更新 attempt_id，旧执行结果不得推进新执行状态。
- 修改同一核心模块的需求由 A 明确依赖或串行处理。
- 同一目标分支的集成串行执行。
- 目标分支更新后，在“最新目标分支 + 本任务”的候选结果上重新验证。
- 已验收版本与候选结果完全一致且验证条件未变化时，可复用对应证据；否则补做受影响验证。
- 合并后确认实际落地版本，并执行约定的冒烟检查。

默认最终合并由用户确认。未来若需要自动合并，应单独确认适用任务范围和门禁。

分别记录 SSH 连接状态、远程进程状态、Agent 会话状态及业务验收状态。连接成功不代表会话可续接，进程结束不代表任务验收成功。断线后先核对实际状态，再决定续接或重试，避免重复修改。持久会话、取消、并发与后台长任务能力需分别验证。

## 10. 完成标准与状态区分

| 状态 | 含义 |
|---|---|
| B 自测通过 | B 的开发侧验证已完成 |
| A 应用验收通过 | A 已实际操作并验证需求结果 |
| 待合并 | 审查与验收通过，等待集成或确认 |
| 已合并 | 对应修改已集成到目标分支 |
| 已完成 | 约定门禁通过、完成合并后检查并归档 |
| 已部署 | 独立生产发布完成；不属于当前流程 |
| 阻塞／未验证 | 缺少访问、环境、确认或证据；不计作通过 |

任务完成检查清单：

- [ ] 有已检查的实施计划；涉及框架选型的决定已由用户确认。
- [ ] 使用独立任务分支与工作目录，修改范围符合约定。
- [ ] B 已自测，记录实际命令、退出码、关键结果及验证范围。
- [ ] A 已审查源码及完整上下文。
- [ ] A 已实际操作应用，所有必需验收场景通过。
- [ ] 验收版本、运行实例和证据一致，缺陷已修复并复验。
- [ ] 候选合并结果已验证，用户确认规则已满足。
- [ ] 已完成合并及合并后检查，报告中明确未验证项和剩余限制。

## 12. 后续 Linux C 端接入边界

Linux C 多为生产环境，当前暂不接入，也不承担开发测试职责。未来单独规划发布流程：

```text
已验收且已合并的结果
  → 用户确认发布版本
  → C 通过 Git 同步指定 commit/tag
  → 执行部署设置
  → 健康检查
  → 记录发布结果；必要时回滚
```

生产部署、服务重启及生产数据写入单独确认。开发完成或合并通过不自动触发生产操作。
